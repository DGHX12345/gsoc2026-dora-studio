## Purpose

解决两个已识别的问题：

1. **常开轮询违背工具软件哲学**。当前 M07（`dora node list` CLI 每 2s）
   和 M08（Jaeger HTTP 每 5s）从后端启动起无条件运行。作为诊断工具，
   监测应是用户主动开启的"诊断模式"，未开启时零开销。
2. **CLI 子进程轮询效率低**。M07 每天 spawn 43,200 个 dora CLI 进程
   （进程创建 + tarpc 连接开销）。M03 已有常驻 Coordinator WebSocket
   客户端，应复用。

## Deliverables

### D1: 监测开关（核心）

- **后端**: `MetricsCollector` 和 `OtelCollector` 重构为可动态启停：
  - 轮询循环由 `tokio_util::sync::CancellationToken`（或 `watch` channel）控制
  - `POST /api/monitoring/toggle` — 开启/关闭监测（body: `{"enabled": true|false}`，
    可带 `{"nodeMetrics": true, "otelSpans": false}` 粒度的细分开关）
  - `GET /api/monitoring/status` — 当前各监测器开关状态 + 运行统计（采样数、上次轮询时间）
  - **默认关闭**。后端启动时不 spawn 任何轮询任务
- **前端**: Performance 页面顶部加监测开关 UI：
  - 主开关 + 每个面板的独立开关（节点指标 / OTel spans）
  - 关闭状态时面板显示"监测已关闭"空状态 + 一键开启按钮
  - 开关状态持久化（localStorage），刷新后恢复
- **开关模式（已定）**: 纯手动。不采用"页面感知"自动启停——切页即断采集
  导致环形缓冲历史不连续，且用户路过页面未必需要监测，自动开启同样是浪费。

### D2: M07 数据源升级 — CLI → WebSocket（核心）

- `MetricsCollector` 的轮询源从 `dora node list` 子进程改为
  `CoordinatorWsClient` 的 `GetNodeInfo` 请求（复用 M03 客户端，常驻连接）
- 解析 `NodeInfoList` 中的 `NodeMetricsInfo`（cpu_usage / memory_mb /
  restart_count / status）—— 注意与 CLI NDJSON 输出字段对齐
- CLI 保留为 fallback：WS 断开时回退到 `dora node list`，与 M03 的
  "WS → CLI → 数据流级状态"逐级回退模式一致
- 轮询间隔仍是 2s，但省去进程 spawn + tarpc 连接重建

### D3: Studio 内置 OTLP HTTP 接收器（可选，Phase 2）

- 目标：Studio 自己监听 4318 作为 OTel 后端，dora 节点直接
  `OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318` 推送 spans，
  省掉 Jaeger 依赖，变为真正的推送模式
- **风险**: OTLP HTTP body 是 protobuf，需要 `prost` + `opentelemetry-proto`
  依赖。必须先验证 Rust 1.75 兼容性（edition 2024 问题同前）。不可行则
  维持 Jaeger 查询模式，此条延后到环境升级后
- **验收前置**: `cargo add prost` 能在 Rust 1.75 编译通过才进入实现

## Acceptance Criteria

- [ ] 后端启动后零监测子进程（`ps` 验证无 dora 轮询、无 HTTP 轮询日志）
- [ ] 开启开关后 ≤2s 内出现首个数据样本
- [ ] 关闭开关后轮询任务完全停止（日志静默，进程数回落）
- [ ] WS 模式下 `dora node list` 不再被调用（日志/统计验证），
      WS 断开时 CLI fallback 自动接管
- [ ] 开关状态跨页面刷新保持（localStorage）
- [ ] 关闭状态下 Performance 页面各面板显示明确空状态 + 开启按钮
- [ ] 现有 79 测试保持通过 + 新增启停逻辑测试（用取消 token 验证循环退出）

## 时机分析

**约束**: GSoC Final Submission 2026-08-24。M09-M14 还有 6 个模块（其中
M12/M13 工具桥接是 proposal 核心交付）。

**建议**: M11.5 放在 **M11 之后、M12 之前**。

理由：
- M09-M11 是 Attribution 线（Layer 4），与监测基础设施正交，无重构冲突
- M11.5 会重构 M07/M08 的 collector 内部结构；放在 M12 前做完，
  后续工具桥接模块可直接受益于"按需监测"基础设施
- 若 M09-M11 进度紧张，M11.5 可整体延后到 Final Submission 之后
  （它是增强而非核心路径），但 D1 的"默认关闭"开关建议尽早做——
  因为它直接回应导师可能提出的"常开轮询开销"质疑

**风险**: D3 (OTLP 接收器) 的 protobuf 依赖兼容性未验证，最坏情况
D3 延期、M11.5 只交付 D1+D2（开关 + WS 复用），仍达成核心目标。
